Git 工作流最佳实践：让协作更高效

2026-03-15 · 7 分钟

团队协作中 Git 的用法至关重要。本文介绍几种主流的 Git 工作流（Git Flow、GitHub Flow），并分享日常开发中的实用技巧。

一、Git Flow

Git Flow 是较早提出的经典工作流，分支角色清晰：

  • main — 生产分支，始终保持可部署状态
  • develop — 开发主分支，汇集所有已完成的功能
  • feature/* — 功能分支，从 develop 分出，完成后合并回 develop
  • release/* — 发布分支，从 develop 分出，用于准备发布版本
  • hotfix/* — 紧急修复分支，从 main 分出，修复后合并回 main 和 develop
# 创建功能分支
git checkout -b feature/user-auth develop

# 完成功能后合并
git checkout develop
git merge --no-ff feature/user-auth

# 创建发布分支
git checkout -b release/1.2.0 develop

适合：有固定发布周期的项目，需要严格的版本管理。

二、GitHub Flow

GitHub Flow 更加轻量，适合持续部署：

  • 只有一个长期分支 main
  • 所有开发在 feature 分支上进行
  • 通过 Pull Request 进行代码审查
  • 合并后立即部署
# 1. 从 main 创建分支
git checkout -b fix-login-bug

# 2. 提交改动
git commit -m "fix: 修复登录状态的 token 过期处理"

# 3. 推送到远程并创建 PR
git push origin fix-login-bug
# → 在 GitHub 上创建 Pull Request

# 4. 代码审查通过后合并
# → 合并后删除远程分支

适合：持续交付/部署的项目，团队规模较小。

三、Commit 规范

好的 commit message 能让项目历史清晰可读。推荐使用 Conventional Commits 规范：

<type>: <简短描述>

[可选的详细描述]

[可选的 footer]

常用的 type 前缀：

  • feat — 新功能
  • fix — 修复 bug
  • refactor — 重构代码
  • docs — 文档变更
  • style — 代码格式调整
  • test — 测试相关
  • chore — 构建/工具链变更

四、实用技巧

交互式变基（Interactive Rebase）

# 合并最近 3 个 commit
git rebase -i HEAD~3

# 使用 squash/pick 来合并或保留提交

stash 暂存

# 暂存当前改动（切换到其他分支）
git stash push -m "WIP: 登录模块重构"

# 恢复暂存
git stash pop

五、总结

选择工作流时，没有银弹。关键是根据团队规模、发布频率和项目复杂度来选择合适的方案。无论选择哪种工作流，保持一致的 commit 规范和执行良好的代码审查流程，才是团队协作效率的真正保障。
